# Webビューア縦スライスの性能計測（2026-07-31）

> **追記（2026-08-01・計画B2）**
> 以下の本文は B1 時点、すなわちワイヤフォーマットが `(H, W, 12)`
> **インタリーブ**だったときの計測である。数値は1つも書き換えていない。
> planar `(C, H, W)` へ変えた後の再計測と、新設した rgb ビュー（`surface`）の
> 計測は末尾の追記1・追記2にある。
> 本文の「プレーナに変えればこのコストはほぼゼロになる」という**予測は
> 半分外れた**。何がどう外れたかは追記1を読むこと。

## 結論

1920x1080x12 float32（94.9 MB）は問題にならない。`fetch` の発行から12枚の
タイルが描き終わるまで **0.70 秒**、12枚連動のパン/ズームは1操作あたり
**0.024 ms**＝60 fpsのフレーム予算の 0.14 % しか使わない。

次期計画（カメラ空間 1.56 GB のワープ）のgo/no-goに対する答えは
**「動くが余裕はない」**。4660x6984 の実行列は18.2秒で読み込めて描画も
できたが、JSヒープを 4192 MB 中 2980 MB（71 %）使い切る。

最も行動に移しやすい発見は、**「GPU転送」時間の93 %がGPUではなくCPUの
デインターリーブである**こと。次期計画のワイヤフォーマットを
`(H, W, 12)` インターリーブから `(C, H, W)` プレーナに変えるだけで、
この時間はほぼ消える。

計測環境: Chrome 150 headless=new（実GPU、SwiftShaderではない）
`ANGLE (NVIDIA, NVIDIA GeForce RTX 3060 Ti (0x00002489) Direct3D11 vs_5_0
ps_5_0, D3D11)`。サーバはループバック。

## 1080p の場合（1920x1080x12 float32 = 99,532,800 B / 94.9 MB）

| 段階 | 時間 |
| --- | --- |
| `fetch` 発行 → `Float32Array` 取得 | **467–492 ms**（193–203 MB/s） |
| ├ うちサーバ側レンダ（最初の1バイトまで） | 約170–186 ms |
| └ うち転送 | 約215 ms |
| 12枚の単チャンネルテクスチャをGPUへ | **176–212 ms** |
| ├ CPUデインターリーブ（207万floatのストライドコピー×12） | **176.7 ms** |
| ├ `texImage2D` ×12 | **13.3 ms** |
| └ `gl.finish()` ×12 | **0.2 ms** |
| クライアント側タイル別分位点（`normalize=per_tile` のときだけ） | 152–162 ms |
| **合計（クリック → 12枚表示）** | **0.70 s**（shared）／ **0.80 s**（per_tile） |

サーバ側の応答は `curl` でも独立に確認した（3回とも
`bytes=99532800`、`total=0.385–0.404 s`、`starttransfer=0.169–0.186 s`）。

### 「GPU転送」の93 %はCPUである

`texImage2D` は13 msしかかからない。対して、インターリーブされた
`(H, W, 12)` から1面ずつ取り出すストライドコピーが177 msかかる。
GPUはほぼ暇で、コストは配列の詰め替えにある。これは画素数×チャンネル数に
比例するので、1.56 GBでは約3.3秒に膨らむ。

**次期計画への含意**: サーバが `(C, H, W)` のプレーナ配置で返せば、各面は
`Float32Array.prototype.subarray` によるゼロコピーのビューになり、この
コストはほぼゼロになる。バックエンド側の変更は小さく、B2規模では効果が
大きい。ワイヤフォーマットを決める前に済ませておく価値がある。

## 表示と再計算の分離（ネットワーク規律）

`window.fetch` を差し替えて呼び出し回数を数えた。

| 操作 | `fetch` 回数 |
| --- | --- |
| 初回読み込み（`POST /session/matrix` ＋ `GET .../view/coef_tiles`） | 2 |
| 露出・γ・カラーマップの変更 | **0** |
| 12チャンネルすべてを読むホバー | **0** |

露出・γ・カラーマップ・ディザはuniformの更新だけでサーバへ行かない、

## B2（カメラ空間 1.56 GB）の実測

`data/color_mixing_matrices.npy`（4660x6984、カメラ空間）は、次期計画が
扱う 1.56 GB そのものである。読み込みも描画も成功した。

| | |
| --- | --- |
| バイト数 | 1,562,181,120（1489.8 MB） |
| `fetch` → `Float32Array` | **14.8 s**（100.7 MB/s） |
| 12枚のテクスチャ転送 | **3.3 s** |
| 合計 | **18.2 s** |
| JSヒープ | **2980.5 MB** / 上限 4192 MB（71 %） |
| レンダラの例外・クラッシュ | なし |

単一の行列でV8ヒープの71 %を使う。比較のために2つ同時に保持する余地は
なく、転送レートもメモリ逼迫下で半減している（100 MB/s 対 196 MB/s）。
18.2秒のあいだ空のグリッドを見続けることにもなる。

**B2への申し送り**: 実現可能ではあるが快適ではない。低解像度プレビューを
先に返して背後で全解像度（あるいはROI）を流す、進捗表示を出す、そして
上記のプレーナ配置に変える——この3点を設計に織り込むこと。

## 追記1: planar `(C, H, W)` へ変更した後（計画B2 Task 1・2026-08-01）

上の「サーバが `(C, H, W)` で返せばこのコストはほぼゼロになる」という予測は
**半分当たり、半分外れた**。同一マシン・同一ブラウザで A/B を取った
（「前」は `routers/view.py` の本体とヘッダの2行だけを戻してクライアントを
インタリーブ経路に落とした状態）。各5回、1回目をJITの暖機として捨て、
残り4回の中央値。

| 指標 | インタリーブ | planar | 差 |
| --- | ---: | ---: | ---: |
| `fetchMs` | 479.8 | **576.5** | **+96.7 ms** |
| `uploadMs` | 165.3 | **12.8** | **−152.5 ms（−92 %）** |
| `rangesMs` | 0.45 | 0.30 | — |
| `totalMs` | 651.4 | **589.9** | −61.5 ms（−9 %） |
| `jsHeapMB` | 380.7 | **191.0** | −190 MB |

`uploadMs` が消えたのは予測どおりである（12.8 ms は B1 が計測した
`texImage2D`×12 の 13.3 ms とほぼ一致し、デインターリーブ分だけが消えている）。

外れたのは「`fetchMs` は変わらない」の方で、**デインターリーブは消えず
サーバへ移った**。numpy の転置＋`tobytes` は 25 ms から 155 ms になり、
その差がそのまま `fetchMs` に乗っている。より安い転置は見当たらなかった
（`moveaxis`・事前確保したループ・`transpose().copy()` のいずれも 152–167 ms）。

**したがって planar を正当化するのは壁時計の −9 % ではなく、クライアント
ヒープの半減（381 → 191 MB）である。** 1080p では12枚の作業用平面 95 MB が
消えるだけだが、後続計画が扱う 1.56 GB のカメラ座標行列では約 1.5 GB に
相当し、その行列は本変更前の時点で JS ヒープ 4192 MB のうち 2980 MB（71 %）を
使っていた（上の「B2（カメラ空間 1.56 GB）の実測」節）。
**`fetchMs` だけを見てインタリーブへ戻してはならない。**

## 追記2: rgbビュー（`surface`）追加後の再計測（計画B2 Task 4・2026-08-01）

計測環境: Chrome 150.0.7871.187 `--headless=new`、
`ANGLE (NVIDIA, NVIDIA GeForce RTX 3060 Ti (0x00002489) Direct3D11 vs_5_0
ps_5_0, D3D11)`（実GPU）。サーバは
`uv run --no-sync python -m uvicorn yoshidacomp_web.app:app --port 8123`、
ループバック。行列は `data/linear_pipeline_1080/matrices_linear_gamma.npy`
（1920x1080x12 float32）。各ビュー5回、1回目を捨てて残り4回の中央値。

計測前にサーバを毎回再起動している。`MatrixStore` は退避を持たず、読み込む
たびに 95 MB が積み上がるため、蓄積した状態で測ると `fetchMs` が 2 割ほど
悪化する（実際に rgb で 2585 ms → 3300 ms の差が出た）。

なお**この機は作業用のデスクトップであって静かなベンチ機ではない**。
下の数値のうち `fetchMs` はセッション間で ±25 % 揺れる。`uploadMs` と
`jsHeapMB` は揺れない。

| 指標 | `coef_tiles`（scalar・12ch・94.9 MB） | `surface`（rgb・3ch・23.7 MB） |
| --- | ---: | ---: |
| `fetchMs` | 631.6 | **2585.1** |
| `rangesMs` | 0.3 | 0.2 |
| `uploadMs` | 13.2 | 19.1 |
| `uploadFinishMs` | 0.2 | 0.1 |
| `totalMs` | **645.0** | **2604.6** |
| `jsHeapMB` | 190.9 | **95.9** |
| 実効転送レート | 150.3 MB/s | 9.2 MB/s |
| 描画タイル数 | 12 | **1** |

### scalar 経路は劣化していない

`uploadMs` 13.2 ms と `jsHeapMB` 190.9 MB は、追記1の planar 実測
（12.8 ms / 191.0 MB）と一致する。サーバ側も `curl` で最初の1バイトまで
0.313–0.329 s と、Task 1 が計測した 0.301–0.329 s に一致した。

`fetchMs` は 580–892 ms とセッション間で散らばるが、これは背景プロセスに
よるもので rgb 経路とは無関係である。`coef_tiles` のサーバ側コードは
planar 化以降1行も変わっておらず（追加されたのはコメントのみ）、
クライアント側で新たに通る分岐も無い。

### rgb は予想より遅い。ただし遅いのはクライアントではなくサーバである

転送量は scalar の 1/4 なのに `totalMs` は**約4倍**になる。

クライアントは速い。`uploadMs` 19.1 ms が、planar → インタリーブの詰め替え
（620万 float）と `texImage2D` 1回の合計である。比較のために書いておくと、
planar 化が消した12チャンネルのデインターリーブは 177 ms だった。1回だけ残る
この複製はWebGLのテクスチャがインタリーブしか受け付けない以上避けられないが、
値段は元の1割程度に収まっている。

遅いのはサーバの描画である。`curl` で最初の1バイトまで（サーバ再起動直後、
暖機後の4回）:

| ビュー | サーバ応答（TTFB） | 全体 |
| --- | ---: | ---: |
| `coef_tiles` | 0.313–0.329 s | 0.409–0.435 s |
| `surface` | **2.103–2.138 s** | 2.128–2.168 s |

同じ行列に対して描画関数を単独で回した内訳（4回、`_render` を直接呼び出し）:

| 処理 | 時間 |
| --- | ---: |
| `coef_tiles._render` 全体 | 152–157 ms |
| `surface._render` 全体 | **2479–2906 ms** |
| ├ `np.linalg.inv`（207万個の3x3、ブール索引経由） | **1464–1766 ms** |
| ├ `np.linalg.det`（同） | 464–476 ms |
| ├ `np.linalg.norm`（フロベニウス・同） | 97–102 ms |
| └ 1/99 パーセンタイル | 約 52 ms |

> **注意（2026-08-01 追記）: この表には2つの内部矛盾がある。次期計画の入力に
> するなら、そのまま最適化の根拠にしてはならない。**
>
> 1. **単独計測（2479–2906 ms）が、同じビューのリクエスト全体の TTFB
>    （2103–2138 ms）より大きい。** 順序が逆である。TTFB はサーバがこの
>    `_render` を呼び終えるまでを含むので、本来は必ず上回るはずである。
>    原因は未特定だが、単独計測はその場で `np.load` した直後に回しており、
>    ページフォルトを含んでいた可能性が高い（サーバ側は `mmap_mode="r"` で
>    読み、暖機後はページが常駐している）。**単独計測は上限値として読み、
>    最適化の対象にするなら TTFB を見ること。**
> 2. **内訳の合計が全体と合わない。** 1464 + 464 + 97 + 52 = 2077 ms に対し
>    全体は 2479 ms で、約 400 ms が未計上である。表に載っていない処理
>    （float64 への複製、`einsum`、`ascontiguousarray`）がその分にあたる。
>
> 追記3で同じ内訳を取り直しており、そちらでは合計と全体が整合している。

**rgb ビューの代金はワイヤフォーマットとは無関係である。** 画素ごとの 3x3
逆行列が全体の約6割、特異判定（`det` と `‖A‖_F`）がさらに約2割を占める。
planar 化も rgb の詰め替えも、この 2.5 秒には触れていない。

**計画B3以降への申し送り（本計画の対象外・計測しただけで手は入れていない）:**

- この行列では `invertible` が全画素 True だった。それでも
  `inverse[invertible] = np.linalg.inv(flat[invertible])` はブール索引で
  149 MB の複製を作り、結果を書き戻すのにもう1回作る。全True のときに
  素通しするだけで数百 ms は縮む見込みである。
- `det` と `‖A‖_F` は特異判定のためだけに 207万回ずつ計算している。
  逆行列側で条件数を見る、あるいは逆行列を作らず `np.linalg.solve` で
  直接解く形にすれば、片方は不要になりうる。
- カメラ座標（4660x6984 = 3250万画素）へ素直に外挿すると、逆行列だけで
  約25秒になる。B4 がこのビューをカメラ座標で使うなら、ROI 限定または
  低解像度プレビューが前提になる。ワイヤフォーマットの話ではないので、
  planar 化ではこの問題は解けない。

## 追記3: `surface` を閉形式に置き換えた後（計画B2 修正波・2026-08-01）

追記2の申し送り「画素ごとの 3x3 逆行列が全体の約6割」に手を入れた結果である。
計測環境は追記2と同じ機・同じ行列（`data/linear_pipeline_1080/
matrices_linear_gamma.npy`、1920x1080x12 float32）。

**逆行列を作るのをやめた。** `A^-1` は画素ごとに1本のベクトルとしか縮約
しないので、9要素を作る必要が無い。`A^T x = (P - b)^T` をクラメルの公式で
直接解く形にした。

| 指標（`_render` 全体、暖機後4回） | `np.linalg.inv` 版 | 閉形式版 | 差 |
| --- | ---: | ---: | ---: |
| 時間 | 2091–2154 ms | **732–755 ms** | **2.8倍速** |
| ピークメモリ（`tracemalloc`） | 650.6 MB | **389.6 MB** | −40 % |

**結果は float32 の本体で完全に一致する。** 622万要素すべてビット一致し、
NaN マスクも一致する。動くのはヘッダの `vmin`/`vmax` だけで、相対 1.4e-8
以下——`np.nanpercentile` が float64 で補間するのに対し、旧実装は float32 の
複製上で補間していたためで、このビューの float32 の刻み（該当値域で 4.8e-7）
の 1/30 以下である。

リクエスト全体でも同じだけ縮んだ（`curl`、サーバ再起動＋暖機後の4回）:

| ビュー | サーバ応答（TTFB） | 全体 | 追記2の TTFB |
| --- | ---: | ---: | ---: |
| `coef_tiles` | 0.293–0.304 s | 0.389–0.402 s | 0.313–0.329 s |
| `surface` | **0.813–0.827 s** | 0.842–0.852 s | 2.103–2.138 s |

`coef_tiles` は 1 行も変えていない対照群で、追記2と一致している。

### 内訳（今回は合計が全体と整合する）

| 処理 | `np.linalg.inv` 版 | 閉形式版 |
| --- | ---: | ---: |
| A の9成分を float64 へ | 48.5–49.8 ms（`(H,W,3,3)` 一括） | 114.9–118.6 ms（面ごと×9） |
| 行列式 | 405.2–420.0 ms（`np.linalg.det`） | 99.6–105.5 ms（閉形式・第1行余因子込み） |
| `‖A‖_F` | 87.3–90.9 ms（`np.linalg.norm`） | 155.8–159.5 ms（2乗和の1.5乗） |
| 逆行列 | **1299–1325 ms**（ブール索引経由） | — |
| 応答の計算 | 76.1–81.8 ms（`einsum`） | 274.6–298.0 ms（余因子×内積×除算） |
| float32 化 | 10.5–10.6 ms（`ascontiguousarray`） | 0 ms（直接書き込み） |
| NaN マスク | — | 13.0–14.0 ms |
| 1/99 パーセンタイル | 56.3–64.1 ms（`isfinite` 複製＋2回） | 38.7–44.5 ms（`np.nanpercentile` 1回） |
| **小計** | 1982 ms | 698 ms |
| **`_render` 全体** | 2091–2154 ms | 732–755 ms |

小計と全体の差（旧109–172 ms／新34–57 ms）は表に出していない小物
（`b` の3面の複製、正則判定の比較、`reshape`）である。

**なぜ「閉形式は個々の項目では遅いのに全体で速いのか」**: 行列式・
フロベニウスノルム・応答計算はどれも単独では閉形式版のほうが遅い。
1300 ms の逆行列がまるごと消えることと、フルサイズの中間配列が4本
（float64 の `a_mat`、`zeros_like`、ブール索引の複製、`inv` の結果、
1080p で各 149 MB）減ることが、それを大きく上回っている。

### カメラ座標では `surface` を断るようにした

上の 732–755 ms・389.6 MB は 207 万画素の値である。
`data/color_mixing_matrices.npy`（4660x6984 = 3250万画素）は 15.7 倍なので
約 12 秒・約 6 GB になる。しかもプロジェクタ座標でない行列は
`active_region` が `None` であり、このビューを正直に保っている NaN マスクが
一切走らない——投影を受けていないカメラ画素にまで「投影面の色」を描く。
遅いだけでなく誤りなので、`ValueError` → 400 で断るようにした。実測で
1.56 GB の行列に対し **5 ms で 400** が返る（B4 でワープを実装するまでの措置）。

### 操作あたりのレンダ回数

サーバ側パラメータはコントロールごとに `change` でフェッチしていたため、
投影コマンドを (1,1,1) から (0,0,0) へ動かすとフルレンダが3回走っていた。
`reqId` が捨てるのは結果だけで、サーバは3回とも計算する。しかも
`render_view` は同期関数なので FastAPI はスレッドプールで走らせ、NumPy の
重い処理は GIL を離すため、3回は並行に実際のコアを食う。適用ボタンで
グループごとに送る形へ変えた（1操作 = 1レンダ）。

上の 0.82 秒と合わせると、この1操作の代金は **約 6.3 秒 → 約 0.85 秒** に
なる。

  残る最大の項目は「応答の計算」275–298 ms と「A の9成分の float64 化」
  115–119 ms で、どちらも 207 万画素×float64 のメモリ帯域で決まっている。
  float32 のまま解けば半減する見込みだが、`_DET_REL_EPS` の判定を
  float32 で行ってよいかの検討が要る。
- カメラ座標の `surface` は上記のとおり現状では断っている。B4 でワープを
  実装するなら、ROI 限定または低解像度プレビューが前提になる点は変わらない。
