# 現在の色補償パイプラインの全挙動

最終監査日: 2026-07-30  
対象ブランチ: `feature/triggered-batch-capture`

この文書は、実装が目指している理想ではなく、現在のコードと設定が実際に行う処理を記述する。未使用機能、近似、量子化、既知の危険箇所も含む。

## 1. 最初に要点

現在の既定実行は `examples/python/sample.py` であり、次の解析逆ガンマ方式を最初から実行する。

1. RGB各4段階、合計64色の全面一様パターンを作る。
2. 有効投影領域722 x 722以外を黒にする。
3. 各パターンへ固定ガンマ2.2の逆特性 `p^(1/2.2)` を適用する。
4. 64枚をCanonのトリガモードで基準露光し、必要なパターンだけ長・短露光を追加してHDR合成する。RAWは常にフル解像度で現像する。
5. カメラの全画素ごとに、カメラ応答RGBから「所望の線形RGB」へ写す4 x 3アフィン行列を推定する。
6. そのカメラ座標行列をdense P2Cでプロジェクタ座標へ補間する。
7. sRGBターゲットを線形化し、各プロジェクタ画素でアフィン行列を掛ける。
8. 0～1へclipし、8bitへ量子化する。
9. 量子化後の補償画像へ再び `p^(1/2.2)` を掛け、実際に投影する8bit PNGを作る。

つまり、現在のモデルは「物体・環境光・プロジェクタ・カメラをまとめて、各位置のアフィン逆写像として学習する」方式である。物理的な前向きモデルを個別に推定して反転しているわけではない。

```text
校正:
所望線形RGB P
  -> 固定逆ガンマまたは実測逆LUT
  -> プロジェクタ
  -> 投影面・環境光
  -> Canon RAW現像
  -> 線形sRGBカメラ応答 C
  -> 各カメラ画素で [C, 1] M ≈ P をfit

生成:
ターゲットPNG/JPEG
  -> sRGB decode
  -> 有効領域へリサイズ
  -> P2Cでカメラ座標Mをプロジェクタ座標へ補間
  -> [target_linear, 1] M
  -> clip + 8bit化
  -> 固定逆ガンマまたは実測逆LUT
  -> 投影用PNG
```

## 3. 色と数値の表現

### 3.1 ターゲット画像

- PNG/JPEGをOpenCVの8bit BGRとして読む。
- RGBへ並べ替える。
- ICCプロファイルや埋め込み色管理情報は読まない。
- 通常のsRGB画像であると仮定し、標準sRGB EOTFで線形RGBへ変換する。
- アルファチャンネルは `IMREAD_COLOR` により使わない。

オフライン再生成スクリプト
`examples/python/rebuild_compensation_with_map.py`には比較実験用の
`--target-decode`がある。`srgb`は上記の既定動作、`gamma`は指定べき乗、
`none`は8bit値を0～1へ正規化するだけで補償計算へ直接渡す。
`none`はsRGB画像を物理的な線形光へ直す処理ではなく、入力コード値を
線形目標値として解釈する明示的な実験モードである。

### 3.2 カメラ画像

コードが「linear RGB」と呼ぶ配列は、RAWセンサー値そのものではない。rawpyで次を行った結果である。

- `gamma=(1, 1)`：トーンガンマなし
- `no_auto_bright=True`
- `bright=1`
- 16bit出力
- `output_color=rawpy.ColorSpace.sRGB`
- `use_camera_wb=True`
- `use_auto_wb=False`
- `no_auto_scale=False`
- フル解像度現像

したがって、実体はカメラWBとrawpyの黒・白レベル処理およびsRGB原色への色変換を通した「線形光のsRGB原色配列」に近いものとなる。分光的に校正された絶対測光値でも、未加工のセンサーRGBでもない。カメラWBが変われば行列も変わる。

各露光の16bit結果を65535で割り、`float32`の0～1へclipする。HDR有効時は
短・長露光を実露光時間比で基準露光相当へ戻して合成するため、合成後配列は
1を超え得る。色行列fitと評価はこの合成後インメモリ配列を使う。

保存用の撮影PNGだけは、標準sRGB OETFで再エンコードして8bit化する。保存PNGは目視用であり、色行列推定には再読込しない。

### 3.3 投影用PNG

最終PNGの8bit値は「ディスプレイへ送るコード値」である。一般写真としてのsRGB見た目を保証する画像ではない。PNGへ色空間や校正条件のメタデータは埋め込まない。

## 4. 64色校正パターン

`num_divisions=4`なので、各チャンネル値は正規化値で `0, 1/3, 2/3, 1`、uint8では `0, 85, 170, 255` になる。

列挙順序はRが最外側、Gが中、Bが最内側で、全組合せ64枚を生成する。各画像は1920 x 1080の全面一様色として一度作られる。

実投影用には `(613, 201, 722, 722)` の外側を黒にする。ただし行列fitの教師値には、マスク前の全面一様な `linear_model_patterns` を使う。教師色は画像左上 `(0,0)` の1画素から読むが、全面一様画像なので全位置で同じ色である。これは有効領域外の黒を教師値として誤用しないための実装でもある。

解析ガンマ方式では、マスク後uint8値を0～1へ直して

```text
display_code = linear_command^(1 / 2.2)
```

とし、再びuint8へ変換する。この変換のuint8化はPyTorchの型変換なので小数を切り捨てる。

物理解像度と論理解像度が一致しており、コードも1920 x 1080画像と
ウィンドウサイズを要求してこのディスプレイへ表示する。

## 6. 高速トリガ撮影とHDR合成

Canon経路では1つのEDSDKセッションを64枚で共有する。セッション開始時にAv、Tv、ISO、画質を設定するが、結果をカメラから再読出ししてログと照合する処理はない。`tolerate_not_supported=True`なので、機種が非対応と返す一部設定は許容され得る。

基準露光の撮影順序は次のとおり。

1. 1枚目を表示し `waitKey(300)`
2. `trigger(wait=True)`
3. 2枚目以降は表示後 `waitKey(300)`
4. 各画像で `trigger(wait=True)`
5. 全トリガ終了後にモードをdisarm
6. RAWを撮影順に現像

`camera.hdr_enabled=true`の場合、基準露光を現像した後、確認ROI
`(4520,1600,480,400)`の値で追加露光が必要なパターンだけを選ぶ。

- 基準露光: 1/15秒。全パターンを撮影する。
- 長露光: 暗部用。1/4秒、必要なら0.5秒まで撮影する。
- 短露光: 飽和部用。1/30秒、必要なら1/60秒まで撮影する。
- 信頼範囲: 8bit換算10～245。最大±3 stop。
- 合成単位: 画素・RGBチャンネルごと。
- 長露光: 基準露光単位へ露光時間比で戻し、飽和していない最長露光で暗部を置換する。
- 短露光: 同様に基準露光単位へ戻し、基準露光で飽和した値だけを置換する。
- 露光比: 要求段数ではなく、実際に選ばれたTvの比を使う。
- 合成値: 1を超えて保持し、色行列fit前にはclipしない。保存用PNGだけは表示用にclipされる。

追加露光は必要なパターンだけ再投影する。追加RAWは1枚ずつ現像・合成して破棄し、
64枚分の基準単位float配列だけを保持する。露光回数分すべてのフル解像度配列を
同時保持しない。

GrayCode校正は専用の別撮影関数を使うため、このHDR処理を通らない。今回の
「GrayCode以外はすべてHDR」という条件はこの経路分離で実現している。

300 msはOpenCVの表示イベントを処理してから撮影トリガを送るまでの安全待機である。同期EDSDKトリガとメモリ転送自体にも約2.4秒/枚かかるが、その時間を「現在の画像が表示完了するまでの保証」としては使わない。2026-07-30の写真ターゲット実写では、1 ms版と300 ms版に同じ固定矩形が写り、これは前フレーム残留ではなく投影面または撮影系の固定特性と判定した。それでもpresent完了をコードが直接計測していないため、標準設定は安全側の300 msとした。

`edsdk-python` v0.2.0の `arm_triggered_capture(transfer="memory")` を使う。受け取ったCR2/CR3/RAWバイト列はホストの一時ディレクトリへ1枚ずつ保存し、全撮影後に読み戻して現像する。現像済みファイルは削除し、終了時に一時ディレクトリも削除する。オリジナルRAWを成果物として永続保存する処理はない。

フレームは撮影順と枚数で対応付ける。各画像内にパターンIDを埋め込んで照合する処理はない。枚数不一致はエラーにするが、同枚数の古いフレーム混入を自動検出する機能はない。前フレーム残りについては実写で目視確認したが、常時の自動検査ではない。

半解像度RAWは次の2箇所で拒否する。

- Canonバックエンド生成時に `half_size=true` なら例外
- RAW現像関数へ `half_size=true` が直接渡されても例外

## 7. 色変換行列の推定

各カメラ画素について独立に4 x 3行列を求める。64パターンのその画素でのカメラ応答を

```text
C = [
  [camera_R_0, camera_G_0, camera_B_0, 1],
  ...
  [camera_R_63, camera_G_63, camera_B_63, 1]
]  # 64 x 4
```

教師となる所望線形RGBを

```text
P = [
  [desired_R_0, desired_G_0, desired_B_0],
  ...
  [desired_R_63, desired_G_63, desired_B_63]
]  # 64 x 3
```

として、

```text
M = solve(C^T C + 1e-6 I, C^T P)  # 4 x 3
```

を計算する。意味は

```text
[camera_R, camera_G, camera_B, 1] @ M ≈ desired_projector_linear_RGB
```

である。最後の1は環境光、黒レベル、定常オフセット等をまとめて吸収するアフィン項になる。

重要な実装上の事実:

- 画素ごとの独立fitで、隣接画素との平滑化や空間正則化はない。
- 正則化は `1e-6 I` のridgeだけ。
- 外れ値除去、反復重み付きfit、ロバスト回帰はない。
- 基準露光は64色を1回ずつ撮り、同一露光の繰返し平均はしない。
- 色行列用撮影はHDRを使い、暗部・飽和部を追加露光で画素・RGBごとに置換する。
- HDR合成後にも信頼範囲外の値が残った場合、それをfitから除外するマスクはない。
- 明示的な暗フレーム減算はしない。アフィン項が一定オフセットを近似する。
- クロストークは3入力 x 3出力の非対角係数として表現できる。
- 非線形性はこの行列自体では表現できない。解析ガンマまたは逆LUTを別に使う。
- 行列はカメラ全4660 x 6984画素について作るため、形状は `(4660, 6984, 4, 3)`、float32で約1.56 GB。
- 有効投影面外の暗い画素にも教師色をfitするため、その領域の行列は物理的に意味を持たない。現在はactive-only P2Cと最終マスクにより通常出力へ使わない。

`safety_margin=0.5`と`min_batch_size=256`はfitのGPU/CPUバッチサイズ推定に使う。`use_gpu=true`ならCUDAを使い、なければCPUへ落ちる。

フル64枚のfloat撮影配列だけで約25 GBになり、fit前の配列化やバイアス付加でも追加メモリを使う。現在はストリーミング最小二乗ではない。

通常の `sample.py` は推定結果を固定パス `data/color_mixing_matrices.npy` に保存する。設定ファイルにはこの経路の行列出力先がなく、方式・露出・マップ・日時のメタデータもnpyへ埋め込まない。現在この固定ファイルは、DISPLAY4を100%へ変更した後にISO400でHDR撮影した解析ガンマ方式の行列で、SHA256は`DD2E83C6843E5454367F0CE6396F73E2E7B36D6B5BBAE5ECBED6EBBE4F7AB38C`である。方式別HDR校正は `calibrate_color_matrix.py` で別ディレクトリへ保存しており、そのメタデータJSONも併記する。通常の `sample.py` または `sample_inverse_lut.py` を再実行すると、固定ファイルは次の新規行列で再び上書きされる。

## 8. 幾何対応と行列ワープ

現在のP2C行は

```text
[projector_x, projector_y, camera_x, camera_y]
```

である。GrayCode step 4 x 4から補間したdense mapを使い、有効投影領域外のcamera座標列はNaNになっている。GrayCode warperはNaN行を除去する。

P2C方式で「カメラ座標の行列をプロジェクタ座標へ移す」ときは、P2Cを逆引き用sampling gridとして使う。

- projector `(x,y)`に対応するcamera `(u,v)`を読む。
- camera行列の12係数をPyTorch `grid_sample`でbilinear補間する。
- pixel-is-point規約で整数座標を画素中心とする。
- `align_corners=False`
- 範囲外paddingはzero
- P2C backward samplingではinpaintしない。

したがって、現在は「カメラ空間で補償値を計算してから画像をワープ」するのではなく、「4 x 3行列の12係数を先にプロジェクタ空間へbilinear補間し、その行列で補償値を計算」する。

この二つはclipなどの非線形処理があるため完全には同値ではない。現在採用しているのは後者である。

P2C行列ワープは本来ターゲットに依存しないが、通常の `sample.py` はターゲットごとのループ内で毎回同じ1.56 GB行列をワープする。現在3ターゲットなら3回繰り返す。今回追加したoffline rebuildはループ外で1回だけ行う。

C2P経路のコードも残っているが、現在の設定では使わない。C2Pを選んだ場合はターゲットをカメラ座標へ逆ワープし、カメラ座標で補償計算後、bilinear splat + mean + 3回convolution inpaintでプロジェクタへ戻す。現在 `c2p_map=""` なので、設定を変えずにC2Pは実行できない。

## 9. ターゲット画像の準備

現在は `target_image_space="projector"` なので、次の処理になる。

1. ファイル名を大文字小文字を無視してソート
2. PNG/JPG/JPEGだけを読む
3. sRGB 8bitから線形float32へ変換
4. 元画像を722 x 722へresize
5. 1920 x 1080の黒画像中 `(613,201)`へ配置

resizeは縮小なら`INTER_AREA`、拡大なら`INTER_LINEAR`。アスペクト比維持、letterbox、cropは行わず、常に722 x 722へ変形する。現在のターゲットは正方形なので意図した使い方では歪まないが、非正方形画像は縦横比が変わる。

線形化してからresizeするため、補間自体はsRGBコード値ではなく線形光で行う。

## 10. 補償画像の計算

プロジェクタ画素ごとの線形ターゲットを `T=(R,G,B)`、ワープ済み行列を `M_p` として、

```text
Q = [T_R, T_G, T_B, 1] @ M_p
Q = clip(Q, 0, 1)
```

をPyTorchのbatch matrix multiplyで計算する。補償計算側は設定の `use_gpu` を見ず、CUDAが存在すれば常にCUDA、なければCPUを使う。

その後、

```text
Q8 = round(255 * Q)
```

としてuint8化する。負値、1超過、プロジェクタで再現できない色は単純clipであり、色域圧縮、知覚的gamut mapping、局所コントラスト保持はない。

さらに有効投影領域外をもう一度黒にする。

## 11. 最終線形化の4方式

現在は方式ごとに別の校正撮影と別の色行列を持つ。行列を方式間で使い回すべきではない。

### 11.1 ガンマ補正なし

`projector_code = Q8`

プロジェクタのネイティブ非線形応答をそのまま含めた状態で、64色行列だけに補償させる。比較実験ではidentity LUTを使う `sample_inverse_lut.py` 相当で校正した専用行列を使用した。

### 11.2 解析逆ガンマ

既定の `sample.py`。

```text
projector_code = floor(255 * (Q8 / 255)^(1 / 2.2))
```

固定2.2、RGB共通、空間的に一様という仮定。色行列校正時の64パターンにも同じ変換を適用する。

関数 `apply_inverse_gamma_correction()` は渡された指数をそのままpowに使う。引数省略時は2.2になり逆方向へ暗くするため、現在のパイプラインは必ず明示的に `gamma=1/proj.gamma` を渡している。

### 11.3 チャンネルランプ実測逆LUT

`sample_inverse_lut.py`で、解析powの代わりにRGB別の1D LUTを使う。LUT方式の64色パターンと最終補償画像の両方に同じLUTを適用し、専用色行列をfitする。

`sample_inverse_lut.py`の既定LUTパターン出力先は`data/inv_lut_proj_patterns`、
最終LUT補償出力は`data/inv_lut_comp_images`である。現在は
`--lut-pattern-dir`と`--lut-comp-dir`を追加しており、実験ごとに別の保存先を
指定できる。線形パターン、撮影PNG、線形補償画像は設定パスを使う。

### 11.4 グレー投影fit実測逆LUT

`source="gray"`として、黒から白までの17段階グレー `(v,v,v)` を投影し、
同じ撮影のR/G/B応答からチャンネル別1D逆LUTを作る。そのLUTを64色パターンと
最終補償画像へ適用し、この方式専用の色行列をfitする。

グレー投影では3チャンネルを同時に刺激するため、プロジェクタ・投影面の
RGB相互作用を測定応答に含む。一方、生成物は依然としてRGB別1D LUTなので、
その相互作用を3D写像として表現するわけではない。

## 12. 実測逆LUTの作り方

現在のルート設定は`source="channel_ramp"`、17レベル、256-entry LUT。

各チャンネルについて

```text
R: (v,0,0)
G: (0,v,0)
B: (0,0,v)
v = 17段階
```

を作るので論理上51パターン。黒 `(0,0,0)` は3系列で重複するため、base exposureのユニーク撮影は49枚。

パターンは逆ガンマを掛けずに生コード値で投影する。カメラのフル解像度linear RGBから `(4520,1600,480,400)` ROIを平均し、投影したチャンネル自身だけを記録する。

HDRが有効で、信頼範囲は8bit換算10～245、最大±3 stop。飽和していれば短く、暗すぎれば長く撮る。最新ISO400チャンネルランプLUTは49基準露光に追加32枚、合計81撮影だった。この実写だけは修正前コードによる基準Tvと同値の冗長長露光9枚を含む。値の合成結果には影響しないが時間を浪費したため、現在のコードでは同一Tvを重複撮影しない。

チャンネルごとに:

1. 同じ入力レベルを平均
2. 黒応答を引く
3. 信頼範囲内の最大応答を白として0～1正規化
4. 単調増加になるよう累積最大
5. `(input_code -> normalized_response)`をPCHIPで密に補間
6. 軸を反転して `(desired_response -> projector_code)`を作る
7. 256点へ保存
8. 前向きfitには`input=0 -> response=0`と`input=1 -> response=1`のアンカーを入れる

逆写像の最終値が必ず`projector_code=1`になるわけではない。信頼範囲内の最大応答が
入力1未満ですでに正規化白へ達すると、`desired_response=1`に対する逆LUT値は
1未満になる。最新ISO400実測では、チャンネルランプLUTの終端がR/G/Bで
約0.876/0.876/0.688、グレーLUTが約0.751/0.876/0.688だった。

グレー方式は17ユニークパターンを使う。最新ISO400実測は基準17枚、
追加13枚の合計30撮影だった。fit手順と256点への反転はチャンネルランプ方式と
同じで、各グレー撮影からR/G/Bすべてを記録する。

これはグローバルなRGB別1D LUTである。

- 位置ごとのガンマ差は表現しない。
- RGB相互作用は表現しない。
- 3D LUTではない。
- 黒と白で正規化するため、絶対輝度や色間ゲインは主に4 x 3色行列側へ残る。

- 撮影PNGを設定先へ書く。

## 14. 幾何だけ変更した場合のoffline rebuild

`examples/python/rebuild_compensation_with_map.py`は撮影しない。

1. 指定した既存カメラ座標行列をmmapで読む。
2. 新しいdense P2Cで行列を1回だけプロジェクタ座標へワープする。
3. 全ターゲットへ同じワープ済み行列を適用する。
4. `none`、`gamma`、`inverse_lut`のいずれかを適用する。
5. 線形補償画像、投影画像、処理時間JSONを保存する。

P2C専用でありC2Pには対応しない。2026-07-30の旧幾何補正版3方式は、
このスクリプトで各方式専用の既存行列から再生成した。現在のISO200/400比較は
offline rebuildではなく、各方式を64色から新規撮影している。

## 15. 4条件または5条件の評価処理

`evaluate_compensation_conditions.py`は標準で次の4条件を各ターゲットについてこの順に投影する。

1. `no_comp`
2. `comp_no_gamma`
3. `comp_gamma`
4. `comp_inverse_lut`

`--gray-lut-comp-dir`を渡すと、5番目に
`comp_inverse_lut_gray`を追加する。全ターゲット分を1回のトリガバッチで撮影する。

各条件の正確な意味:

- `no_comp`: 元のsRGB 8bitターゲットをそのまま722 x 722へresizeして投影。線形化も逆ガンマも色補償もない。
- `comp_no_gamma`: 専用色行列の出力コードをそのまま投影。
- `comp_gamma`: 専用色行列 + 固定2.2解析逆ガンマ。
- `comp_inverse_lut`: 専用色行列 + 単独RGBチャンネルランプからfitした実測RGB別逆LUT。
- `comp_inverse_lut_gray`: 専用色行列 + グレー投影からfitした実測RGB別逆LUT。

撮影結果は:

1. linear RAW captureをP2Cでプロジェクタ座標へwarp
2. sRGB 8bitへ変換
3. active領域だけをcrop
4. 元ターゲット解像度へ `INTER_AREA` resize
5. 元のsRGBターゲットと比較

評価値:

- PSNR: sRGB 0～1のRGB全要素MSE
- SSIM: 11 x 11 Gaussianを用いた独自実装をRGB配列へ適用し、全画素・全チャンネル平均
- Delta E76: OpenCVでfloat sRGBからLabへ変換し、画素ごとのユークリッド距離を平均

色管理された測色器評価ではない。カメラ、rawpy、sRGB仮定を含む画像ベース評価である。物体の凹凸、貼り合わせ、遮蔽、表面反射も誤差に含む。最後に元画像サイズへresizeするため、プロジェクタ1画素単位の幾何誤差をそのまま報告する指標でもない。

## 16. 現在していないこと

以下はコードや設定名が存在する、または一般的な色補償で期待され得るが、現在の本番経路ではしていない。

- `paths.rpcc_matrix`は未使用。`apply_rpcc_correction()`関数はあるが `sample.py` から呼ばれない。
- カメラRGBを測色XYZへ正規校正していない。
- ICCプロファイルを使用しない。
- 分光反射率やプロジェクタSPDを推定しない。
- 物体、環境光、プロジェクタ、カメラを別モデルへ分離しない。
- 物理前向きモデルを反復最適化していない。
- 3D LUTを使わない。
- 行列の空間平滑化をしない。
- 色行列撮影の同一露光繰返し平均、外れ値除去、HDR合成後の不良値除外をしない。
- 最終出力の知覚的色域圧縮をしない。
- 投影後に結果を見て自動再補正する閉ループ処理はない。
- 色校正中に幾何を再推定しない。
- カメラ設定の実値を撮影ごとにread-backして保存しない。
- RAW原本を成果物として保存しない。
- 保存PNGへ校正条件を埋め込まない。
- 通常 `sample.py` では処理時間JSONを保存しない。
- 通常 `sample.py` は巨大行列ワープをターゲットごとに繰り返す。
- 非正方形ターゲットのアスペクト比を維持しない。
- Windows側の色管理、HDR、スケーリングを固定・検証しない。

## 17. 校正が無効になる条件

現在の色行列は次を一体として学習しているため、どれかが変われば原則として再校正が必要。

- 投影面の形状、位置、貼り物、定規、遮蔽物
- プロジェクタ位置、フォーカス、ズーム、輝度・色設定
- カメラ位置、フォーカス、レンズ、WB
- ISO、Av、Tv
- 周囲光
- 投影ウィンドウ位置・有効領域
- ガンマなし、解析ガンマ、チャンネル逆LUT、グレー逆LUTという前段線形化方式

幾何だけが変わり、カメラと投影面の測光応答が本当に同じなら、既存カメラ座標行列をoffline rebuildで新P2Cへワープし直せる。ただしセットアップ変更が反射や露出にも影響した場合は、64色撮影からやり直す必要がある。

## 18. 実測結果

### 18.1 HDR導入前の単一露光結果

DISPLAY4を100%へ変更後、方式ごとに専用の64色校正を行い、
3画像 x 5条件を同一バッチで撮影した平均。

### ISO200

| 条件 | PSNR [dB] | SSIM | Delta E76 |
| --- | ---: | ---: | ---: |
| 補償なし | 15.72 | 0.7884 | 26.72 |
| 補償あり・ガンマなし | 18.29 | 0.7491 | 16.87 |
| 補償あり・解析逆ガンマ2.2 | **19.77** | **0.7956** | **13.53** |
| 補償あり・チャンネル逆LUT | 19.34 | 0.7810 | 15.97 |
| 補償あり・グレー逆LUT | 19.50 | 0.7941 | 14.60 |

ISO200では解析ガンマが平均3指標すべてで最良だった。グレー逆LUTは
チャンネル逆LUTより平均3指標すべてで良いが、解析ガンマには届かなかった。

### ISO400

| 条件 | PSNR [dB] | SSIM | Delta E76 |
| --- | ---: | ---: | ---: |
| 補償なし | 20.03 | **0.8426** | 23.60 |
| 補償あり・ガンマなし | 19.96 | 0.7453 | 15.92 |
| 補償あり・解析逆ガンマ2.2 | 22.94 | 0.7917 | **13.77** |
| 補償あり・チャンネル逆LUT | **23.29** | 0.8216 | 14.49 |
| 補償あり・グレー逆LUT | 21.00 | 0.7668 | 17.83 |

ISO400では全条件中のSSIM最高は補償なし、補償方式中のPSNR・SSIM最高は
チャンネル逆LUT、Delta E76最小は解析ガンマであり、単一の最良方式はない。
グレー逆LUTはチャンネル逆LUTと解析ガンマの両方より悪かった。

ISO200白投影では確認ROIの0.98以上を含む画素が55.4%だった。
ISO400ではコード170ですでに17.4%、白255では99.998%となり、
白はほぼ全画素・全RGBが飽和した。現行64色fitは飽和画素を除外しないため、
ISO400の各方式はこの強い飽和を含んだ行列である。

5条件比較の撮影・現像API時間はISO200で63.10秒、ISO400で63.30秒。
いずれも15枚を1回のトリガバッチで撮影した。

### 18.2 最新ISO400 HDR結果

設定はAv14、基準Tv 1/15秒、ISO400、300 ms、フル解像度RAW。
GrayCodeは既存P2Cを再利用し、逆LUT、方式別64色行列、最終投影結果、
4段階グレーをHDR撮影した。

通常のsRGBターゲット3画像に対する平均:

| 条件 | PSNR [dB] | SSIM | Delta E76 |
| --- | ---: | ---: | ---: |
| 補償なし | 19.73 | **0.8316** | 24.23 |
| 補償あり・ガンマなし | 18.26 | 0.7112 | 24.76 |
| 補償あり・解析逆ガンマ2.2 | 19.29 | 0.7446 | 24.52 |
| 補償あり・チャンネル逆LUT | **22.51** | 0.8072 | **14.91** |
| 補償あり・グレー逆LUT | 21.09 | 0.7449 | 17.20 |

補償方式中ではチャンネル逆LUTが3指標すべてで最良だった。ただし、
同じISO400の単一露光結果に対してHDRが全方式を改善したわけではない。
グレー逆LUTのPSNRは+0.09 dB、Delta E76は-0.64改善した一方、
他の多くの指標は悪化した。HDRで1を超える放射応答を復元できても、現在の
画素別4 x 3アフィンモデルがその非線形な広ダイナミックレンジ応答を十分に
表現できるとは限らない。これは結果からの推定であり、悪化原因を一意に
同定したものではない。

4段階グレーの確認ROI平均線形値は、コード0/85/170/255に対して
`0.00125 / 0.13178 / 0.74689 / 1.60141`で単調増加した。
白のRGB平均は約`1.806 / 1.111 / 1.888`であり、単一露光ならclipされる
1超の値をHDR合成で保持できた。

詳細、方式別行列ハッシュ、撮影枚数、速度比較、car/car-newの直接入力結果は
`docs/hdr_full_recalibration_iso400_20260730.md`に記録する。
