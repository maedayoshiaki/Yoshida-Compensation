# パス入力欄のファイル選択 設計仕様

作成日: 2026-08-05
対象: `packages/web/yoshidacomp_web`（ビューア）

## 1. 目的

ビューアの4つのパス欄はすべて手打ちである。パスを覚えているか、別のウィンドウから
コピーしてくるかしないと何も読めない。ここにファイル選択を足す。

| 要素id | 用途 | 種別 | 位置 |
| --- | --- | --- | --- |
| `path-input` | 行列 `.npy` | ファイル | `static/index.html:12` |
| `target-path` | ターゲット画像 | ファイル**または**ディレクトリ | `static/index.html:144` |
| `lut-path` | 逆LUT `.npz` | ファイル | `static/index.html:156` |
| `gen-output-dir` | 投影画像の出力先 | ディレクトリ（**書き込み先**） | `static/index.html:215` |

## 2. スコープ

### 対象

- 閲覧API `GET /api/browse` の追加
- `Host` ヘッダ検査ミドルウェアの追加（4節。マシン全体を閲覧可能にするための前提）
- 上表4欄それぞれの `参照` ボタンとモーダルのファイラ
- ディレクトリ選択時の「新規フォルダ名」欄

### 対象外

- ファイルの作成・削除・改名。ファイラはディスクを一切変更しない。
- アップロード。ブラウザからファイルの中身を送る経路は作らない。
- 読み込み処理そのものの変更。ファイラはテキスト欄を埋めるだけで、
  `POST /api/session/matrix` / `/api/target` / `/api/lut` / `/api/generate` の
  4経路は現状のまま動く。
- テキスト欄の手打ちの廃止。欄は今まで通り編集可能なままにする。

## 3. ブラウザからサーバのパスを渡せない理由

`<input type="file">` は選ばれたファイルの**サーバ側の絶対パスを返さない**（ブラウザの
セキュリティ制約により、`File.name` と中身しか取れない）。バックエンドはパス文字列を
受け取って自分でディスクから読む設計なので、この経路は使えない。使おうとすると
99MBの `.npy` をアップロードし直すことになり、ディレクトリ選択に至っては表現できない。
Explorer からのドラッグ&ドロップも同じ理由で不可（`DataTransfer` もパスを渡さない）。

したがって**ディレクトリの一覧はサーバが返す**。ブラウザはそれを描いて選ばせるだけ。

## 4. 閲覧範囲と `Host` ヘッダ検査

ファイラはマシン全体を閲覧できる（リポジトリ配下に限定しない）。その判断の根拠と、
そのために必要になる対策を記す。

**追加されない危険**

- サーバは `127.0.0.1` 束縛で起動する（`AGENTS.md` 3.3）。LANの他機からは届かない。
- `app.py` に CORS ミドルウェアは無い（`app.py:1-5` が「同一オリジンで配信するため
  CORS は不要」と書いている通り）。他オリジンのページは GET を*送れる*が、
  `Access-Control-Allow-Origin` が無いため**応答を読めない**。
- `POST /api/session/matrix` は既に任意の絶対パスを読み（`routers/session.py:54`）、
  `POST /api/generate` は既に任意のパスへ書く。閲覧APIは到達範囲の*種類*を増やさない。

**追加される危険と対策**

一覧できることは、パスを当てられることより実際上は強い。そして CORS による保護は
**DNS リバインディングで迂回できる** — 攻撃サイトが自ドメインを `127.0.0.1` に
再解決させると、ブラウザから見て同一オリジンになり CORS の判定自体が発生しない。
uvicorn は既定でこれを防いでいない。

対策として、Starlette の `TrustedHostMiddleware` を `create_app()` に入れる。
自前で書かない ── ポート除去と一致判定はこのミドルウェアの仕事そのもので、
`.venv` に入っている実装を読んで挙動を確認済みである。

```python
app.add_middleware(TrustedHostMiddleware,
                   allowed_hosts=["127.0.0.1", "localhost", "testserver"])
```

確認した挙動と、それに伴う仕様の確定：

- 拒否は **400 `Invalid host header`（plain text）**。403 ではない。本文は JSON では
  ないので `api.js::errorMessage` の「`detail` が無ければそのまま出す」経路に落ちる。
- ホスト部は `headers.get("host", "").split(":")[0]` で取る。**IPv6リテラルは扱えない**
  （`[::1]:8123` は `[` になる）。サーバは IPv4 ループバック束縛なので `::1` では
  そもそも到達できず、実害は無い。`allowed_hosts` に `::1` を書いても効かないため書かない。
- `testserver` を許すのは `TestClient` の既定 `base_url` がこれだからである。
  既存の `TestClient(...)` は11ファイル85箇所にあり、全部に `base_url` を渡すのは
  この変更に見合わない。**DNS リバインディングは名前解決を要する攻撃**であり、
  `testserver` は単一ラベルで登録可能なドメインではないので、ブラウザにこの
  `Host` を送らせる経路が無い。Host ヘッダを自由に作れるローカルのプロセスは
  そもそもソケットへ直接届くので、この検査の対象ではない。

この検査を入れない限り「マシン全体を閲覧可能にしても安全」とは言えない。両者は
セットである。

## 5. 閲覧API

```
GET /api/browse?path=<str>&suffixes=<.npy,.npz>
```

`path` を省略すると `Path.cwd()`（サーバはリポジトリルートから起動されるので、
現在の欄に入っている相対パスと同じ基準になる）。

```json
{
  "path": "C:/py_scripts/Yoshida-Compensation/data",
  "parent": "C:/py_scripts/Yoshida-Compensation",
  "roots": ["C:/", "D:/"],
  "entries": [
    {"name": "linear_pipeline_1080", "is_dir": true, "size": null, "mtime": 1753...},
    {"name": "matrices_linear_gamma.npy", "is_dir": false, "size": 99532800, "mtime": 1753...}
  ],
  "total": 128,
  "truncated": false
}
```

- `parent` はドライブ直下では `null`。`roots` は Windows の存在するドライブ一覧で、
  ドライブをまたぐ移動に使う。
- **ディレクトリは `suffixes` で消さない。** フィルタはファイルにのみ適用する。
  消すと目的のファイルがある階層へ辿り着けなくなる。
- 並び順は**ディレクトリ先・ファイル後、いずれも casefold 順**。
  casefold なのは `target.py::_listing`（`target.py:111`）がこの順で `names` を作り、
  `LoadTargetRequest.index` がその添字だからである。画面の並びと `index` の基準が
  ずれると、選んだつもりのない画像が読まれる。
- 上限は1回あたり2000件。超えた場合も `total` に実数を入れ `truncated: true` を返し、
  UIは「12800件中2000件を表示」と明示する。黙って切り詰めない。
- 再帰しない。1階層ずつ返す。隠しファイルも除外しない。
- `roots` は Windows では存在するドライブ（`C:/`, `D:/` …）。それ以外のOSでは `["/"]`
  の1要素とする。フロントは中身を解釈せず、そのまま選択肢として出す。

**エラー**

| 状況 | 応答 |
| --- | --- |
| 存在しない | 404 |
| ディレクトリでない | 400 |
| 読む権限が無い（`C:/System Volume Information` など） | **403** |

`PermissionError` を 500 にしない。Windows のマシン全体閲覧では通常操作で踏む。
（`Host` 検査による拒否だけは 400 で、これはミドルウェアの応答であり本APIのものではない。）

**テスト可能性の制約**

`os.listdir` はモジュール経由で呼ぶ（`import os` して `os.listdir(...)`、
`from os import listdir` にしない）。NTFS は名前順で返すため、テストが本当に
未整列の入力を渡せないと**並び順のテストが落ちられなくなる**。
`target.py:88-91` が同じ理由で同じことをしており、そこには実際に落ちない
テストを書いてしまった経緯が記録されている。

## 6. フロントエンド

新規モジュール `static/js/filepicker.js`。`main.js` からは開く関数1つだけを使う。

各欄の隣に `参照` ボタンを置き、押すとモーダルが開く。

| 欄 | モード | フィルタ |
| --- | --- | --- |
| `path-input` | ファイル | `.npy` |
| `target-path` | ファイルまたはディレクトリ | `SUPPORTED_TARGET_IMAGE_SUFFIXES`（サーバが返す） |
| `lut-path` | ファイル | `.npz` |
| `gen-output-dir` | ディレクトリ ＋ 新規フォルダ名 | — |

**拡張子はフロントに書かない。** `GET /api/browse/suffixes` を1つ足し、
起動時に取得する。

```json
{"matrix": [".npy"], "target": [".png", ".jpg", ...], "lut": [".npz"]}
```

`target` の出所は `yoshidacomp.compensation.pipeline` の
`SUPPORTED_TARGET_IMAGE_SUFFIXES` ひとつだけ。`.png,.jpg,...` をフロントに書くと
同じ集合の2つ目の出所ができる。`matrix` と `lut` も同じ表に載せて、4欄すべての
フィルタが1箇所から来るようにする。

**構成**

```
┌─ 行列 .npy を選択 ────────────────────────┐
│ [C:/ ▾]  C:/py_scripts/Yoshida-Compensation/data │
│ [↑ 上へ]                          128件中128件   │
├──────────────────────────────────────────────────┤
│ 📁 comp_test_20260724/                           │
│ 📁 linear_pipeline_1080/                         │
│ 📄 matrices_linear_gamma.npy       99.5 MB       │
├──────────────────────────────────────────────────┤
│ （dirモードのみ）新規フォルダ名: [__________]    │
│ → data/proj_20260805                             │
├──────────────────────────────── [取消] [選択] ───┤
└──────────────────────────────────────────────────┘
```

**操作**（2026-08-06 訂正。当初の記述と実装が食い違っていた箇所と、
作らなかったものを分けて書く）

- ディレクトリは**シングルクリック**で進入、`↑ 上へ` で親へ。
  当初は「ダブルクリック」と書いていたが、実装はシングルクリックであり、
  そちらを仕様とする。クリック1回に動作1つであること、`file_or_dir` の欄では
  1回目のクリックが「ファイルの選択」でもあり、二重クリック待ちにすると同じ
  1回目の意味が待ち時間で決まってしまうこと、押したときに返る文字列は
  `#picker-chosen` が常に表示していて推測が要らないこと、の3点による。
- ファイルはクリックで選択、`選択` で確定。
- `Esc` と背景クリックで取消。**実装済み**（`filepicker.js::wireOnce`）。
- 開いたらフォーカスをダイアログ（`#picker`、`tabindex="-1"`）へ移し、
  閉じたら開いた `参照` ボタンへ戻す。**実装済み**（`pickPath` と `close`）。
  体裁の問題ではない: 背景の裏の `参照` にフォーカスが残ると Space / Enter で
  2度目の `参照` が走り、`session` が `close()` を経ずに差し替わって1つ目の
  呼び出しの Promise が宙に浮く（`navigate` の `mine` の注記にある状態に、
  キーボードだけで到達できる）。
- `↑` `↓` による行の移動と、`Enter` による進入・確定は**未実装**。
  フォーカスをモーダル内に閉じ込める（Tab が背後へ抜けない）ところまでも
  **未実装**で、閉じ込めているのは `Esc` と戻し先だけである。
  この2つは実装計画に落ちておらず、意識的に見送ったのではなく落ちた。
  作っていないものを仕様に残さない。

**確定時の副作用**

テキスト欄に値を書いたうえで、**`input` と `change` イベントを実際に発火させる**。
`gen-output-dir` は編集されると上書き合意が失効する仕組みを持っており（
`tests/test_web_frontend_js.py` の「`上書き` の確認は1つのディレクトリについてのもの」）、
イベント無しに値だけ差し替えると「Aについての合意をBに使う」状態を作れてしまう。

**書き込む形式**

`Path.cwd()` の配下なら相対パス、外なら絶対パス。現在の欄の見た目
（`data/linear_pipeline_1080/matrices_linear_gamma.npy`）を保つため。

**新規フォルダ**

ディレクトリモードでは現在地の下に「新規フォルダ名」欄を出し、
`現在地 + "/" + 入力名` を返す。**ファイラはディレクトリを作らない。**
実際の作成は従来通り `POST /api/generate` の実行時にサーバが行う。
入力が空なら現在地そのものを返す。

**エラー表示**

403 / 404 / 400 はモーダル内に出す。モーダルは閉じず、直前のディレクトリに留まる。
ページ下部のステータス行には出さない（モーダルに隠れて読めない）。

## 8. 実測（2026-08-06、2026-08-06 レビュー指摘により再測定・訂正）

`packages/web/yoshidacomp_web/browse.py::list_directory` を直接呼んで計測した。
以下の各範囲は、そのディレクトリ**自身**を複数回計測した結果のみで作った
（別ディレクトリの計測値を混ぜていない）。単発（1回のみ）の値はその旨を明記し、
複数回再現した値と同列に扱わない。生コマンドと生出力は
`.superpowers/sdd/2026-08-05-path-file-picker/task-5-report.md` の
「Fix round 1」節に貼ってある。

**実利用域: `data/`**

| ディレクトリ | 件数 | 応答時間（自身の計測のみ） |
| --- | --- | --- |
| `data/`（直下） | 57 | 2.7〜4 ms（4回: 4, 3.4, 2.7, 2.8 ms） |
| `data/graycode_recalibration_20260805_window4` | 10 | — |
| `data/linear_pipeline_1080` | 18 | — |
| `data/iso160_nonhdr_20260805_geom` | 12 | — |
| `data/debug`（`data/` 配下を `os.walk` で探索した実際の最大） | 139 | 6〜9 ms（6回: 9, 9, 8, 6.6, 6.2, 6.2 ms） |

`data/` 配下でエントリ数が最大のディレクトリは `data/debug` の139件で、2000件に
対し十分な余裕がある。応答は一桁ミリ秒。

**閲覧範囲がマシン全体（4節）である以上の worst case**

`data/` の外も測った。System32 と WinSxS は挙動が異なるため分けて書く。

キャッシュを意図的に破棄する手段が無いため、「冷キャッシュ」という列は作らない。
観測できたのは「同じディレクトリを続けて測ったうちの**最初の1回**が遅かった」ことだけで、
それが冷キャッシュによるものかは確かめていない。以下ではその通りに書く。

| ディレクトリ | 件数 | 2回目以降（複数回、再現） | 最初の1回（1回のみ、未再現） |
| --- | --- | --- | --- |
| `C:/Windows/System32` | 4880 | 146〜170 ms（6回: 160, 152, 170, 152, 146, 154 ms） | 738 ms（1回のみ） |
| `C:/Windows/WinSxS` | 29537 | 1174〜1274 ms（6回: 1274, 1190, 1232 ms が自分の計測。1189, 1174, 1185 ms はレビュアーによる独立した再測定で、自分では未再現） | 2400 ms（1回のみ） |

`System32` は繰り返し測った値がすべて300ms未満で安定している。738msは他の巨大
ディレクトリと同時に測った際の最初の1回のみの値で、再現を試みていない（上記の通り、
遅かった理由も特定していない）。**`System32` を「300msを超える」側に含めない。**

`WinSxS` は繰り返し測っても一貫して300msを超える（自分の3回に加え、レビュアーの
独立した3回も同じ範囲）。最初の1回の2400msも同じく1回のみで未再現であり、これを
「1.2〜2.4秒」のような幅として書くと、6回とも1.2秒前後に収まる再現値の上に
1回しか出ていない値を上限として載せることになり誤解を招く。そのため繰り返し計測の
範囲（1174〜1274ms）とは別枠で扱う。

**`MAX_ENTRIES` を変えてもこの遅さは解決しない**

`list_directory()` は `os.listdir()` の後、全エントリを `sorted()` してから1件
ずつ `is_dir()` と `stat()` を呼び、`ordered[:MAX_ENTRIES]` で最後に切り詰める。
打ち切り件数は返す JSON の大きさにしか効かず、時間のかかる処理（全件の stat）
は `MAX_ENTRIES` の値と無関係に走る。実測で確認した: 同一ディレクトリ
（`C:/Windows/System32`、4880件）を `MAX_ENTRIES=2000/200/50` で計測し、
152/146/154ms と統計的な差がなかった。

**結論**

`MAX_ENTRIES = 2000` のままとする。

- 実利用域（`data/`）には十分な余裕があり、応答は一桁ミリ秒。
- マシン全体には `WinSxS`（29537件、繰り返し計測で再現して1174〜1274ms）のように
  2000件・300msの両方を超えるディレクトリが実在する。`System32`（4880件）は
  件数こそ2000を超えるが、繰り返し計測での応答は300ms未満で安定しており、300msを
  超えた事例は最初の1回のみの計測（738ms、未再現。理由は特定していない）に限られる。
- `MAX_ENTRIES` はいずれの場合も応答時間を左右しない（上記の通り実測済み）。
  値を下げても速くならず、上げても実害はない。
- 巨大ディレクトリでの高速化（全件 stat をやめる、走査を打ち切るなど）は
  `list_directory` の構造を変える話であり、本節が閉じるべき論点
  （2000件という上限に根拠があるか）とは別の話として対象外とする。
